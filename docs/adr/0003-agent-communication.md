# ADR-0003: Reconcile desired state through jittered HTTPS polling

Status: Proposed - for Xiaoyu and mentor review  
Scope: Week 1 decision; API in Week 2 and agent implementation in Week 5

Choose agent-initiated HTTPS pull: GET /v1/robots/{id}/desired-state with ETag/If-None-Match and a proposed five-second interval with independent +/-20% jitter. Unchanged state returns 304 without a database write; authentication and credential revocation are checked even on that path. At 20 agents, desired-state polling averages four requests/second; five-second heartbeats add approximately four more, a planning load to measure rather than a benchmark result. Use outbound proxy configuration and avoid any robot-side inbound listener. This fits Rover's intermittent cellular/site Wi-Fi and Senpai's restricted school networks. WebSocket and MQTT can also run outbound and provide lower-latency notifications, but require persistent-session recovery, keepalives and, for MQTT, broker operations. They do not remove the need to reconcile missed desired state after a disconnect. Reject persistent push for the initial implementation because the target is reliable deployment rather than real-time motion control. A later push notification may trigger an early poll without becoming the source of truth. Basis: personal plan pp. 5-7, 10-11 and the mentor-confirmed shared-platform scope.

Keep desired state in the registry's PostgreSQL data, separate from reported state; the controller writes targets and agents report observations. The proposed contract carries a monotonic desired-state revision, target digest, compatibility constraints, and a short activation lease issued and renewed only by the controller; authenticated 200/304 responses convey its persisted expiry. Agents cache verified artifacts and their last known-good slot, resume interrupted Range downloads, and revalidate current desired state before activation; an ETag alone never authorizes execution. Retry transient failures with bounded exponential backoff and jitter, initially capped at 30 seconds outside an active rollout and 10 seconds during one; honor Retry-After. After a proposed 30-second lease expires, continue the current model and defer new activation. If the controller is down, the registry can still serve its last persisted target, but an expired rollout lease prevents further activation and no cohort advances. If the registry is also unavailable, agents retain the current model, journal bounded status locally, and reconcile on recovery. Connectivity recovery checks revision and trust freshness before resuming or discarding staged bytes, avoiding activation of a superseded target. These timings are assumptions for Weeks 5-6 tests; the programme's 60-second rollback target must be measured from health breach and may not be represented as achievable for an indefinitely disconnected robot. Local smoke-test rollback remains independent of cloud connectivity. Week 1 implements neither this protocol nor an agent.
