# ADR-0002: Use content-addressed object storage and Ed25519 signatures

Status: Proposed - for Xiaoyu and mentor review  
Scope: Week 1 decision; packaging and verification implementation in Week 3

Keep the plan's MinIO for reproducible local development fixtures; target Azure Blob Storage for the later cloud adapter. MinIO's [official repository](https://github.com/minio/minio) is archived, its README states that it is unmaintained and source-only, and legacy binaries receive no updates. Week 1 local validation confirmed a successful build of official release RELEASE.2025-10-15T17-29-55Z from commit 9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a, using archive SHA-256 45521908307306e925c98d629e1c17d78c8b72b6ee242b1bfb1409f7d8ee5841; authenticated object-store readiness passed. This replaces unavailable legacy Docker Hub/Quay images for the local fixture; see [the validation report](../W01_Validation_Report.md#reproducible-storage-fixture). Pin the selected source commit, Go toolchain and builder/base-image digests; record source URL, licence, build command, architecture and resulting binary/image SHA-256. Accept a legacy image only with an immutable digest and documented provenance; never depend on latest. This contains acquisition drift, not upstream maintenance risk, so the fixture is not a production-storage recommendation. MinIO's S3 API and Azure Blob are different: a storage adapter and contract tests must cover authorization, Range reads, conditional requests, errors and immutability rules before a production claim. Use SHA-256 of canonical manifest bytes as logical package identity; the manifest binds payload-file and deterministic-archive hashes, contracts, compatibility, provenance and licence. Detached signatures prevent self-reference. Store immutable objects under sha256/<artifact_digest>/, make identical publication idempotent, and keep lifecycle/approval/audit in PostgreSQL. Azure's [Get Blob contract](https://learn.microsoft.com/en-us/rest/api/storageservices/get-blob) supports ranges and conditional reads; this does not establish full adapter parity.

Choose Ed25519 through Python cryptography for a small on-device verification contract. A separately privileged registry signing component signs a domain-separated manifest digest after validating publication; origin/integrity does not imply evaluation quality or approval. Cosign also supports blobs, self-managed keys and offline bundles; defer its richer identity/provenance integration rather than dismissing it as container-only or always-online. See [Ed25519 verification](https://cryptography.io/en/stable/hazmat/primitives/asymmetric/ed25519/), [cosign blob signing](https://docs.sigstore.dev/cosign/signing/signing_with_blobs/), and [bundle verification](https://docs.sigstore.dev/cosign/verifying/verify/). Robots pin public keys/key identifiers; signing private keys never enter robots, Git, images, logs or publisher credentials. The git-ignored development key is available only to the signer. Rotation distributes a versioned trust bundle authenticated by a separately provisioned offline bootstrap root, confirms receipt, switches signing keys, then retires the old key after explicit overlap; compromise skips overlap. Agents reject unsigned, wrong-key, revoked-key, invalid-signature and hash-mismatched artifacts. Expired trust blocks new activation while the last healthy model remains available; offline devices learn revocation only after reconnecting and refreshing trust. An ETag is a cache validator, not integrity proof. Week 7 drills rotation and validates cloud secret handling without assuming managed-HSM algorithm support. Basis: personal plan Section 1.4 and pp. 6, 8-9, 12; Rover resume and Sentinel audit constraints. No Week 1 signing or Azure implementation is claimed.
